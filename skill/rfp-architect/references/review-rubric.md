# RFP 審查 rubric（review 模式的 WHAT to check）

review 模式逐項套用本 rubric，輸出**依嚴重度分級的 findings**。HOW（流程與輸出格式）在 SKILL.md。

## 審查心法（寫 finding「為什麼重要」時的依據）

- **RFP 是風險定價的資訊揭露機制**：每個沒寫清楚的條款，誠實廠商會加風險溢價、投機廠商會低價搶標再靠變更賺回；模糊不會更便宜，只把成本推遲到爭議。→ 指出缺漏時，講清楚它如何推高報價或埋下爭議，比泛泛說「不完整」有力。
- **可驗收性貫穿全程**：寫不出驗收標準的需求＝還沒想清楚的需求。缺驗收標準幾乎都是 Blocker。
- **最有利標 ≈ 成果導向採購前身**：評選規則一旦公告不得變更（剛性）；遇到要求敏捷 / SOO 的政府案，提醒剛性與彈性的張力。

## 嚴重度定義

- **Blocker（阻擋）**：會導致採購無效、法律風險或必然爭議。例：評選委員會組成不合法、評選配分未載明、缺驗收標準、缺智財歸屬約定。
- **Major（重大）**：顯著降低提案品質或可比較性、易引發超支 / 變更。例：需求模糊、範疇未界定含 / 不含、預算完全不揭露、無釋疑機制。
- **Minor（輕微）**：可改善但不致命。例：用語不一致、缺里程碑細分、無 PoC 安排。

## 審查清單（逐項判定：符合 / 缺漏 / 不足）

### 1. 文件定位與範疇
- [ ] 用對文件（RFP 而非 RFQ；得標後事項未誤置於 RFP）。
- [ ] 工作範疇明確劃分「包含 / 不包含」（防範疇蔓延）。— 缺 = Major
- [ ] 業務背景、痛點、量化目標清楚。

### 2. 需求品質
- [ ] 功能需求分級（必要 / 應有 / 加分）。
- [ ] 每條需求可驗證、對應驗收標準。— 缺驗收標準 = Blocker
- [ ] 非功能需求量化（效能 / 安全 / 可用 / 可維護）。— 缺 = Major
- [ ] （維護 / 擴充案）系統測試上線、新舊系統轉移、技術移轉需求明列。— 缺（且屬維護 / 擴充案）= Major（與「退場 / 資料返還」不同，此為履約中轉換）

### 3. 台灣法制與程序（政府採購案）
- [ ] 招標 / 決標方式選定且適切（異質採購→最有利標；資訊服務→公開評選或最有利標，見 `taiwan-procurement.md` §2 三條路徑）；採最有利標者已報上級機關核准（法 §56 第 3 項）。
- [ ] **應載事項齊備**：逐項對照 `taiwan-procurement.md` §9。評選項目與子項、配分或權重、評定方式、合格判定（§4、§16–§18）— 缺 = Blocker；協商時得更改之項目、淘汰情形（有此安排者）— 缺 = Major
- [ ] 評選項目與採購目的有關、能分辨廠商差異、明確合理可行、子項不重複（《最有利標評選辦法》§6）。— 不符 = Major；疑似有利或不利於特定廠商 = Blocker
- [ ] **規格未綁標**：未指定特定商標、專利、型式、來源地或供應者，無法精確說明者已註明「或同等品」（法 §26 第 3 項）；資格未不當限制競爭（法 §37）。— 違反 = Blocker（`rfp_lint.py` 不檢查，須人工判定）
- [ ] **價格配分 / 權重落在 20%–50%**（《最有利標評選辦法》§16 評分、§17 序位評比）。— 價格納入評選且非固定價格案低於 20% 或高於 50% = Blocker（明文禁止，決標可被爭議）。**固定價格給付案**（§9 第 2 項、§12 第 3 款、§15 第 1 項第 3 款）價格得低於 20%，須明載；**價格不納入評分**者（§12 第 2 款、§13）無此區間——判定前先確認屬哪一種，避免誤報。
- [ ] 簡報及現場詢答若列為評選項目，配分 / 權重 ≤ 20%，且載明簡報不得更改投標文件（§10）。— 逾 20% = Major
- [ ] 未把「未出席簡報」寫成排除廠商的事由（§10 第 4 項：不影響投標文件之有效性；該項不給分可）。— 違反 = Major
- [ ] 評選委員會組成合法（5 人以上、專家學者 ≥ 1/3、召集人一級主管以上）。— 違反 = Blocker；**政府最有利標 / 資服案完全未載評選委員會與評選方式 = Blocker**（`rfp_lint.py` 已對此升級嚴重度）。
- [ ] 等標期符合 `taiwan-procurement.md` §7 金額級距；釋疑機制明定。— 無釋疑 = Major
- [ ] （資訊服務案）逐款對照《機關委託資訊服務廠商評選及計費辦法》§5 得載事項與 §7 評審項目——用 `info-service-article5-map.md` 對照表，輸出「§5 第 N 款 缺漏（嚴重度）」。§5 是「得視個案載明」，finding 不可寫成違法。— 缺關鍵款項 = Major；有獨立「應」字法源或交集驗收 / 智財 / 評選者 = Blocker
- [ ] （公開評選案）議價方式已載明（§11），未訂固定服務費用者已規劃底價（§12）。— 缺 = Major
- [ ] （整體委外案）§6「應另行載明」事項齊備，含過渡作業計畫、機關資訊人員轉任與權益保障、變更處理之計費原則；期間 ≤ 10 年。— 逾 10 年 = Blocker；其餘缺 = Major

### 4. 資安與在地化（見 clause-library.md）
- [ ] 資安分級與對應控制。— 公部門缺 = Blocker（注意：章節僅寫「不處理 / 不適用」不算具備，`rfp_lint.py` 會以 out_of_scope 警示）。
- [ ] **委外資安事項**（《資通安全管理法》§10、施行細則 §7，對照 `clause-library.md` S）：資安人力、複委託、事件通報、終止處理、機關稽核。— 政府軌缺 = Major
- [ ] **客製化開發的安全性檢測**：要求廠商提供檢測證明；屬核心資通系統或委託金額達 1,000 萬元者，機關已規劃自行或另行委託第三方檢測。— 達門檻未規劃 = Blocker
- [ ] 危害國家資通安全產品限制（§11）、涉及國家安全之廠商資格限制（已敘明理由及必要性並核准）、SSDLC、資安標章 / 無障礙 / HTTPS（依標的）。
- [ ] 資料落地、繁中在地化。— 缺 = Major；涉個資 / 雲端 / 關鍵系統時 = Blocker。
- [ ] （涉個資）委託監督事項對照《個人資料保護法施行細則》§8 六款與定期確認。— 缺 = Major
- [ ] （AI / 資料 / 雲端標的）對照 `clause-library.md` O–R：AI 條款（模型版本 / 評估指標 / 幻覺率 / 人工覆核 / 訓練資料使用 / log 保存 / 公平性）、資料治理（字典 / 血緣 / 品質 SLA / 權限矩陣 / 去識別化）、雲端韌性（RTO / RPO / DR 演練 / 金鑰 / 備份不可竄改）、供應鏈（SBOM / 授權 / 弱點修補 SLA / 映像掃描）。— AI / 關鍵雲端案缺核心條款 = Major 以上。

### 5. 契約、驗收、智財、保固
- [ ] 履約 / 驗收 / 付款條件前置揭露。
- [ ] 智財歸屬提供可勾選選項（未留空）、含素材授權，並載明侵害第三人合法權益時由廠商負責（《資訊服務辦法》§21）。— 缺 = Blocker；僅寫「另行約定」視同缺（`rfp_lint.py` 以 `out_of_scope_mention` 提示）
- [ ] 若可能分包，已約定分包商著作權之取得義務與證明文件交付期限；全部或主要部分交由他廠商履行屬轉包，不得為之（法 §65）。— 缺（且確有分包）= Major
- [ ] （資訊服務案）計價及付款方式擇定法定計費法（總包價 / 計時 / 成本加公費），成本加公費案載明公費 ≤25%、管理費 ≤100% 等上限。— 缺 = Minor
- [ ] 保固期間與維護範圍、SLA 與罰則。

### 6. 變更管理與退場（最常被整章漏掉）
- [ ] 變更管理 / 變更請求流程於 RFP 揭露（提出 / 影響評估 / 書面核准）。— 缺 = Major（範疇蔓延的主因）
- [ ] 退場、資料返還與移交條款（資料以開放格式返還、不主張留置、配合後手接管）。— 公部門 / 關鍵系統缺 = Major

### 7. 治理與盡職調查
- [ ] 機關側決策窗口 / 溝通節奏明定。
- [ ] 要求廠商揭露實際參與團隊名單與資歷（非掛名人力）。— 缺 = Minor
- [ ] 視標的安排 PoC / 啟動期技術評估。— 大型 / 高風險案缺 = Minor

### 8. 評選透明與流程
- [ ] 評選標準於 RFP 內揭露。
- [ ] 預算範圍揭露（利於技術 / 價值取捨）。— 完全不揭露 = Major
- [ ] 提交格式、頁數、時程、聯絡窗口完整。

## 投標廠商立場的審查

委託者是投標廠商時，RFP 不是對方能改的文件，每項 finding 都要換成對方能採取的行動：

- **能問就問**：可能影響報價的模糊處，寫成可直接送出的**釋疑**問題，於招標文件規定之日期前以書面提出（法 §41）。
- **違法才異議**：認為違反法令致損害權利或利益者，提出**異議**：對招標文件規定為公告或邀標次日起等標期之 1/4（不得少於 10 日），對釋疑、變更或補充為接獲通知或公告次日起 10 日（法 §75）。公告金額以上案件不服處理結果可申訴（法 §76）。
- **問不到就定價**：釋疑後仍不明確的項目，列為報價風險與投標假設，標出影響投標與否的決策項。
- 嚴重度依同一定義，但改用投標方語意：Blocker＝不釐清就不宜投標；Major＝須計入風險溢價；Minor＝履約時留意。

## RFP 八大常見錯誤（review 對照表）

1. 範疇與要件不明確 → 廠商以假設填空。
2. 過度聚焦功能清單，忽略要解決的業務問題。
3. 忽略交付與協作現實（時程、產能、決策者、工作方式）。
4. 不分享預算範圍。
5. 易選錯夥伴（只看銷售簡報，未盡職調查）。
6. 溝通落差（時區、文化、非同步）。
7. 輕忽法律 / 契約（聯合協議、智財、爭議解決）。
8. 必要要件回應機制不足（必要要件＝合格 / 不合格，非評分）。

## 委外失敗根因（findings 的「為什麼重要」可引用）

- 首要：**需求模糊＋溝通不良**；一份雙方解讀不同的高層簡報 → 做出錯的東西。
- 次要：**範疇蔓延**（客戶初期不確定、不了解變更後果）→ 延誤 / 超支 / 品質下降。
- 預防：需求鎖定、正式治理（角色 + 24h 決策者）、供應商盡職調查、結構化溝通、**正式變更請求流程**，並在 RFP 階段就寫入**變更管理與退場 / 資料返還**條款。

## Finding 輸出格式（每項）

```
[嚴重度] 章節/位置 — 問題簡述
- 為什麼重要：<風險 / 後果，可引用根因或法制>
- 建議修正：<具體、可貼入的改寫或補充；指向 clause-library.md 條款>
```

投標廠商立場把最後一行換成：

```
- 建議行動：<釋疑問題全文 / 異議理由與期限 / 報價假設>
```
